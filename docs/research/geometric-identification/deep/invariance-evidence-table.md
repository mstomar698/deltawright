# Invariance evidence table — what drifts by how much

GWALI · Alameer-Halfond i18n-failure study · Browserbite · X-PERT/XFix · WebSee · Kraus AGS · Romano flaky-UI · CLS/Layout-Instability spec · Chromatic/Applitools · GUI-Perturbed. Every number below is traced to a full-text read (§10); anything not directly measured is marked **unmeasured**.

## 1. What it does

**GWALI (Alameer, Mahajan, Halfond, ICST 2016).** Builds a "Layout Graph" (LG) of every visible HTML tag *and* text run from browser-rendered bounding boxes, labels each pair with direction/alignment/containment relations, diffs a baseline-locale LG against a translated-locale LG over k-NN neighbourhoods, filters expected text-reflow noise with three heuristics, and ranks suspicious elements for the developer. On 54 real sites: 91% precision / 100% recall / median localisation rank 3 / 9.75 s per page.

**Alameer & Halfond, ICSME 2016.** Reuses GWALI as a measurement instrument, not a detector, over 2,241 baseline/translated page pairs (449 sites, 12 languages); 1,020 pairs had matching enough structure to compare. Quantifies *how much* a page's visual-relation graph actually changes under locale swap.

**Browserbite (Saar, Dumas, Kaljuve, Semenenko; SPE 2015/ICSM 2013).** Pure screenshot-to-screenshot cross-browser testing: Harris-corner detection → morphological joining → blob Regions of Interest (ROI), each with centroid/size/orientation via image moments; ROIs matched between browsers by centroid+size+orientation, with normalised-cross-correlation search as fallback; a 17-feature ML classifier (decision tree / 3-layer NN) filters the geometric matcher's false positives.

**X-PERT / XFix (Mahajan, Alameer, McMinn, Halfond, ISSTA 2017).** X-PERT (Choudhary et al., cited not re-implemented) detects "layout XBIs" — cross-browser layout inconsistencies — via an alignment-graph comparison and returns `⟨label, e1, e2⟩` tuples (e.g. `⟨top-align, e1, e2⟩`). XFix consumes X-PERT's output and *repairs* it: a two-phase search finds CSS-property values that minimise a three-term geometric fitness function, then combines per-XBI fixes into one patch.

**WebSee (Mahajan & Halfond, ICST 2015).** Screenshot-vs-oracle comparison using Perceptual Image Differencing (spatial/luminance/colour sensitivity models, tunable Δ/F/L/C parameters) instead of pixel-exact diffing; difference pixels are DBSCAN-clustered, then mapped back to HTML elements via an R-tree of browser-rendered bounding rectangles.

**Kraus, Rößler, Sulzmann (2020), "Visual Testing of GUIs by Abstraction."** Replaces pixel diffing with an Abstract GUI State (AGS): each element is a flat set of key→value attributes (id, class, x, y, width, height, text, …); three "fairly similar" relations of increasing looseness re-identify an element between a golden master and a new run, so GUI-change detection becomes attribute-set comparison, not image comparison.

**Romano, Song, Grandhi, Yang, Wang (ICSE 2021), "An Empirical Analysis of UI-based Flaky Tests."** Manually root-causes 235 flaky UI tests from 62 web/Android projects, producing a taxonomy that includes DOM Selector Issue and Layout Difference as distinct, quantified root-cause categories.

**Layout Instability API / CLS (WICG draft + web.dev).** Chromium's own in-browser mechanism for deciding "did this node's box meaningfully move," expressed as a viewport-normalised impact-fraction × distance-fraction score with a UA-defined pixel-significance floor.

**Chromatic `diffThreshold` and Applitools match levels (industry docs).** Two commercial visual-testing products' documented dead-bands: Chromatic's colour-space perceptual threshold and anti-aliasing filter; Applitools's Strict/Layout/Dynamic match-level hierarchy, where Layout mode is explicitly a relative-position (not absolute-pixel) comparison.

**GUI-Perturbed (Wang et al., 2026).** Not a DOM-geometry paper — a VLM-grounding robustness benchmark — included here because it is the cluster's only source with a controlled, isolated zoom perturbation and a measured accuracy delta, exposing what happens when "geometry" is encoded as raw screenshot pixel coordinates rather than page-relative structure.

## 2. Exact representation

**GWALI's LG:** complete graph ⟨V, F⟩; node = ⟨type∈{Element,Text}, c1=(x1,y1), c2=(x2,y2), xpath⟩ where c1/c2 is the element's Minimum Bounding Rectangle from `getBoundingClientRect`-equivalent browser APIs at a fixed viewport; edge label set R = {North,South,East,West} ∪ {Top/Bottom/Left/Right-Aligned} ∪ {Contains, Intersects}, derived by pure coordinate comparison (e.g. `v.y2≤w.y1 ⇒ North`). Hidden/zero-size/non-layout tags are excluded by a CSS-property + heuristic filter; inline tags inside one text run are merged into one node.

**Browserbite ROI:** size, centroid (x,y) from raw image moments M_ij = ΣΣ x^i y^j I(x,y), orientation θ from 1st/2nd-order central moments. Ground-truth incompatibility rule (hand-labelled): position Δ > 40 px (either axis) OR size Δ > 15 px (height or width) OR visible colour/visibility change. 17-D classifier feature vector = 10 intensity-histogram bins + NCC correlation + baseline (x,y,w,h) + a 1–14 browser-platform config index + page-level mismatch density (E/T).

**X-PERT/XFix:** XBI = ⟨label, e1, e2⟩, label ∈ {top-align, …} naming which alignment relation broke. XFix's fitness = w1·Δpos + w2·Δsize + w3·Δnpos, weights (2, 1, 0.5) resp. (size prioritised). Δpos = Euclidean(TL_R,TL_T) + Euclidean(BR_R,BR_T) between reference- and test-browser bounding boxes; Δsize = |w_R−w_T| + |h_R−h_T|; Δnpos sums Δpos over all DOM neighbours within N_r hops (N_r=1 ⇒ parent+children).

**WebSee:** PID difference-pixel set D_P (tunable Δ,F,L,C); DBSCAN clusters (no predefined k); R-tree of element bounding rectangles maps each difference pixel to the HTML elements it falls inside, O(log n) per lookup vs O(n) for a DOM-tree walk.

**Kraus AGS:** element = (attribute-set, [children]) flattened to (attribute-set, []). Attribute keys split into strong set I_s = {id, path} (must match/be similar) and weak set I_w = {type, x, y, width, height} (presence-only, value ignored) — i.e. **position/size are explicitly excluded from the identity test**. Three "fairly similar" relations: ≈₁ exact strong-key equality; ≈₂ per-key Jaro-Winkler similarity ≥ t on strong keys (t=0.9); ≈₃ average key-match rate ≥ u across I_s∪I_w (u=0.3). Pixel diffs ≤ 25 are globally ignored.

**CLS:** per layout-shift entry: previousRect/currentRect (viewport CSS px) for up to 5 sources ranked by impact area; `value = (impact-region-area/viewport-area) × (max-move-distance/max(viewport-w,viewport-h))`; a node counts as shifted only if its start point differs by ≥ a UA-defined "pixels to significance" (spec cites **Chrome = 3 px**) on either axis; pure CSS `transform` and container-internal scroll are excluded; `hadRecentInput` is true if the last input was < **500 ms** ago.

**Chromatic:** per-pixel YIQ colour-space distance; `diffThreshold` default **0.063** (range 0–1, 0=most sensitive); anti-aliased pixels auto-detected and excluded unless `diffIncludeAntiAliasing` is set.

**Applitools Layout mode:** proprietary element segmentation of the two screenshots + a "relative positions of these elements are consistent" check (no numeric threshold published); floating regions = (element rect, permitted-movement bounds rect) pair.

**GUI-Perturbed:** ground-truth is an axis-aligned bounding box on the rendered screenshot; a model outputs an (x,y) click point (or a bbox in coordinate-mode) in raw screenshot-pixel space at a stated `{h,w}`; Precision variant applies `ScaleViewport(browser, 0.7)` before the Playwright screenshot — a genuine layout re-zoom, not a post-hoc image resize.

## 3. Algorithm

GWALI: render at fixed viewport → strip hidden/non-layout tags → for each node compute 5 anchor points (4 corners + centre) → k-NN (Java Spatial Index) per point, k scaled to |V| → union = neighbourhood → diff only neighbourhood edges via a WebDiff-style probabilistic XPath/attribute matcher M → symmetric-difference δ per edge → apply the 3 filtering heuristics → suspiciousness score = Σ(edge memberships) + Σ|δ|, sorted descending. Runtime breakdown (avg 9.75 s/page): 36.1% browser load, 60.1% MBR collection, 0.2% graph build, 3.65% comparison, 0.01% filtering.

Browserbite: grayscale → Harris corner detector → morphological dilation joins dense corner pixels into blobs → per-ROI moments → nearest-match by (centroid, size, orientation); unmatched ROIs get an NCC search inside a bounded window, SSD-thresholded; then the 17-feature classifier (MATLAB decision tree / 1-hidden-layer feed-forward NN) re-labels each candidate pair.

XFix: 5-stage loop — (1) `getXBIs` via X-PERT; (2) map each XBI label to relevant CSS properties (hand-built label→property table); (3) per-root-cause local search (hill-climbing with exploratory moves) against the 3-term fitness; (4) biased-random combinatorial search over candidate fixes, guided purely by the *count* of XBIs after applying a candidate repair; (5) re-run `getXBIs`, terminate on ∅, no-improvement, or regression. Median runtime **14 minutes**; `searchForCandidateFix` = 67% of total time, `searchForBestRepair` = 32%.

WebSee: screenshot → PID(Δ,F,L,C) → DBSCAN clustering of difference pixels → build R-tree of element MBRs once per page → per cluster, per pixel, R-tree point-query → union of hit elements → heuristic expansion (hidden-element rule etc.).

Kraus AGS: extract flattened attribute sets for old/new DOM → for each of the 3 relation instances, greedy best-match pairing (ties broken by overall match score) → diff attribute sets of matched pairs. Mean runtime per test-run: ≈₁ 6,517.72 ms, ≈₂ 6,350.37 ms, ≈₃ 5,822.29 ms (range 1.2–61 s across 400 runs, 20 sites × 2 browsers × 10 reps).

CLS: browser-internal, O(1) amortised per composited frame per tracked node; no user-facing algorithm to run, only an event stream to consume.

## 4. Act step and verification

None of GWALI, Browserbite, WebSee, Kraus-AGS, CLS, Chromatic or Applitools's Layout mode performs a click/type/drag — all are **detection/assertion** tools; "verification" is a human- or ground-truth-labelled oracle (GWALI: 30 true-positive + 24 true-negative pages, manually inspected; Browserbite: the 40 px/15 px hand rule; Kraus: manual TP/FN/FP categorisation of 320 introduced changes by "multiple people"). Applitools's separately-read *visual locators* feature (`eyes.locate`) is the cluster's only industrial act step: it returns matched-template coordinates and the caller is told to "simulate mouse and keyboard events using the standard browser device handler methods" at that point — i.e. act = synthetic input at a returned (x,y), verify = none published.

**XFix is the only source in this cluster with a genuine act-then-verify loop over geometry.** The act is "apply this CSS value," and verification is closed-loop: re-run the same detector (`getXBIs`) and require the XBI count to strictly decrease, with a fixed-point/regression check preventing an infinite or harmful loop. A second, independent verification used a **human study**: participants rated before/after similarity to a reference on a 0–10 scale; 78% of participant responses showed improved consistency, 8% showed decreased consistency (net RQ1 result: XBIs cut 86% mean/93% median by X-PERT's own detector, 99% mean/100% median by human observation) — i.e., an automatic geometric-fitness fix and a human's subjective visual judgment agreed most, but not all, of the time.

GUI-Perturbed's "act" is a single-shot click prediction scored against ground truth (hit-in-bbox), with no retry/verify loop — the paper's diagnosis of *why* it fails (memorised absolute screen position) is itself evidence for why an act step needs a re-verify against live geometry rather than a cached coordinate.

**Recommended tolerances/units, each anchored to a cited number:**

1. **Position dead-band ≈ 3 px at native resolution, expressed as a *viewport-distance-fraction* beyond that.** CLS's own "pixels-to-significance" default (Chrome = 3 px) is the only browser-shipped, currently-live number for "did this box actually move" — reuse the *concept* (a small fixed-px floor before any comparison runs) but express the graded magnitude as CLS's `distance-fraction = shift / max(viewport_w, viewport_h)`, since that is what generalises across viewport/breakpoint and zoom, unlike a flat px cutoff.
2. **Do not gate element *identity* on position/size at all — treat them as weak (presence-only) keys, in every matching mode.** Kraus's AGS gets 79.53%/92.10% precision/recall across two browsers *and* two resolutions with x/y/width/height in the weak set I_w (checked for presence, not value) in all three of its "fairly similar" relations. The one relation that instead loosened its *strong* keys (id/path) from exact equality to a Jaro-Winkler similarity test (≈₂, t=0.9) — leaving position equally weak — still produced 21,440 diffs against only 320 introduced changes (9,946 "deleted" + 10,881 "created" vs ≈₃'s 50/43), because fuzzy id/path matching mis-paired distinct elements; the lesson generalises to position too: *any* identity key that is allowed to be "close enough" needs a validated similarity threshold, not an ad hoc one.
3. **Size dead-band as a relative, not absolute, threshold.** Browserbite's hand-tuned 15 px absolute cutoff was derived on desktop-scale ROIs (140 pages) and is falsified by its own cited example (a live element measuring 368.7×15 px in Chrome vs 298.4×16 px in IE11 — a ~70 px, ~19% width delta on ordinary browser-engine noise, an order of magnitude past the 15 px rule); recommend a fraction of the element's own baseline size instead of a flat px number.
4. **Order/alignment-relation flip threshold ≈ 45° of angular change between two elements' centres**, GWALI's own α parameter, validated end-to-end (91% P / 100% R, 54 apps) — but GWALI's own false-positive post-mortem (large text-shrink cases exceed 45° without a real layout break) shows this constant must be normalised by the elements' separation distance, not left as a flat degree cutoff.
5. **Containment/alignment slack should be structural, not numeric**: GWALI's best-performing heuristic ignores an alignment-relation change entirely when the containing element has spare capacity (Text/Text or Text/Element edges only) — a rule about DOM/CSS structure (does the parent have room?), not a pixel number, and it is what separates GWALI's 91% precision from WebSee/X-PERT's 55% on the same 54-app corpus (both flag *any* geometric change as failure).
6. **Two independent dead-bands, never merged into one:** a geometric (position/size) tolerance and a perceptual/colour tolerance. Chromatic's own documentation warns that raising `diffThreshold` (default **0.063**, YIQ colour distance) to suppress noise "may hide positioning changes" — direct, vendor-stated evidence that colour-noise tolerance and position tolerance must stay separate knobs, matching Kraus's separate 25 px pixel-diff ignore vs. AGS attribute-identity design.
7. **Prefer DOM-native units (CSS px from post-layout `getBoundingClientRect`, or viewport-fraction) over raw screenshot pixels for the primary representation.** GUI-Perturbed's failure mode is specific to models that memorise *absolute screenshot-pixel* coordinates; a zoom event that a DOM read would see as an ordinary, correctly-scaled CSS-pixel layout is instead a 3.3–7.9 pp accuracy cliff for pixel-grounded models — the clearest cited argument in this cluster for keeping geometry DOM-native and falling back to screenshot/VLM grounding only when DOM access is unavailable.

## 6. Invariances shown / NOT shown

- **Shown — text-driven container growth without a real layout break (GWALI):** the alignment-forgiveness heuristic (only fire on alignment changes for Element/Element edges, not Text/* edges inside a container with spare room) is validated end-to-end at 91% precision vs. 55% for tools (WebSee, X-PERT) that treat any geometric delta as failure.
- **Shown — cross-browser rendering noise up to ~40 px/15 px on desktop screenshots (Browserbite):** the bare geometric matcher alone (centroid+size+orientation, no ML) still achieves recall 0.98 but precision only 0.66 — i.e., geometric matching *tolerates* the noise for recall, but a learned filter (classifier, F 0.923) is required to reject false incompatibilities at that same tolerance.
- **Shown — identity across two browsers *and* two resolutions when position/size are weak keys (Kraus):** 79.53%/92.10% P/R with x/y/width/height merely required present, not equal — the strongest direct evidence in this cluster that *identity* survives geometric drift precisely by *not* keying on geometry.
- **Shown — sub-3-px jitter and pure CSS transforms (CLS spec):** explicitly excluded from "shift" by browser design; scroll inside `overflow` containers likewise excluded.
- **NOT shown — RTL/mirrored layout:** GWALI explicitly does not handle Arabic/Farsi/Hebrew page mirroring; flagged as a limitation, not evaluated.
- **NOT shown — DPR or theme (light/dark) drift:** zero sources in this cluster isolate either axis; both are blank rows in §5.
- **NOT shown — zoom invariance for pixel-grounded (screenshot-coordinate) representations:** GUI-Perturbed's own diagnosis states models "click on elements that occupy the spatial position where the target appeared at the original scale," i.e. the representation *actively encodes* an absolute-pixel prior that a 70% zoom breaks; relational instructions ("above X") are hurt *more* than direct-naming ones (up to 7.9 pp vs 3.3 pp), meaning the spatial-relation reasoning itself, not just the anchor lookup, is not zoom-invariant in this model class.
- **NOT shown — a single agreed dead-band unit across the cluster.** GWALI/Browserbite/X-PERT/XFix all use raw px; Kraus mixes raw-px pixel-diff (25) with unitless similarity scores (t, u); only CLS and Chromatic use a normalised (viewport-fraction / colour-space-distance) unit — no cited source in this cluster runs the same tolerance sweep in two different units to show which travels better across viewport resize.

## 7. Failure modes

- **GWALI:** (1) z-index-layered content (sliders/carousels) is flattened to one 2-D layer by the LG, merging independent slides → false positives (named cause #1 of GWALI's own 9% imprecision). (2) The fixed α=45° direction-change threshold is a flat constant; large text-shrink cases can legitimately exceed it without a real IPF → false positive (named cause #2). (3) No RTL support (design limitation, not an evaluated failure rate).
- **Alameer/Halfond ICSME:** i18n Checker configuration failures: **27%** of all reported CFs across 449 sites were severity "Error" (undefined-render-behaviour), rising to 30% for automatic-translation-framework sites vs 21% for server-side-resource-file sites — a measured severity split by *how* the site is internationalised, not just *whether*.
- **Browserbite:** bare-bones (no classifier) geometric matching alone has precision **0.66** (recall 0.98) — i.e. roughly 1 in 3 flagged incompatibilities on 140 real pages is a false positive from geometry-only matching; the paper explicitly analyses which of the 17 features (histogram bins, correlation) drive false positives to motivate the classifier layer.
- **WebSee:** its own hidden-element expansion heuristic (add a hidden node to the result set if its visible parent/child/sibling is already flagged) is explicitly named by the authors as improving recall while "introduc[ing] false positives" — a documented recall/precision trade-off baked into one rule.
- **XFix:** two named systematic failure scenarios — (1) X-PERT never included the true faulty element in its detected set X to begin with, so no repair search can find it; (2) the local search fails to converge to an acceptable fix due to the search's own non-determinism. Empirically, 8% of human-study responses rated the "repaired" page as *less* consistent than before, i.e. the automated geometric fitness function and human visual judgment disagreed in a non-trivial minority of cases.
- **Kraus AGS:** the ≈₂ (per-key Jaro-Winkler test) relation is the paper's clearest quantified failure mode of over-loose matching — it reports **21,440** differences against only 320 actually-introduced changes (160 per browser), because a too-lenient "fairly similar" test mismatches elements, which then cascades into spurious created/deleted-element diffs (9,946 "deleted" + 10,881 "created" out of that total, vs. ≈₃'s 50/43).
- **Romano:** Async Wait alone accounts for 45.1% (105/235) of all flaky UI tests — the dominant confound that any geometry-based stability check must be paired with (not replace); Layout Difference (10/235, 4.3%) and DOM Selector Issue (16/235, 6.8%) are the two categories this cluster's geometric methods most directly target, and together are still a minority (~11%) of observed flakiness.
- **CLS:** by design, `PerformanceObserver` "layout-shift" entries expose at most **5** sources per entry ("arbitrary but balanced" per spec text), so a frame with many simultaneous shifts can under-report which elements moved; entries with `hadRecentInput` true (within 500 ms of the last input) are excluded from the aggregate score, which can hide a real regression if it happens to follow user input.
- **Chromatic:** vendor documentation itself warns that setting `diffThreshold` too high (example given: 0.8) "may hide positioning changes" — a direct, cited admission that the perceptual dead-band and the geometric dead-band are not the same axis and conflating them creates false negatives.
- **GUI-Perturbed:** style/text-shrink perturbations flip a comparable fraction of individual predictions to zoom (14.9%/15.5% vs 15.5% for precision) but are *not* net-degrading (near-symmetric 378-degraded/320-improved split, b/c ≈1.2:1) — unlike zoom's asymmetric 485-degraded/241-improved (b/c ≈2.0:1, McNemar significant in 9/12 configs) — i.e. the failure mode is specifically the *directional* nature of the zoom-induced error, not mere prediction instability.

## 8. What to borrow for a DOM-first geometric web locator — and what to avoid

1. **Build GWALI's Layout Graph with CDP/Playwright primitives, not GWALI's own O(complete-graph) construction.** Replace per-node `getXPosition/getYPosition`-style JS calls with one batched `DOMSnapshot.captureSnapshot` (layout tree + bounding boxes in one round trip) or `page.evaluate(() => elements.map(e => e.getBoundingClientRect()))`; keep GWALI's relation predicates verbatim (`v.y2≤w.y1 ⇒ North`, equality tests for alignment, rectangle-containment test for Contains/Intersects) but only compute them over a k-NN neighbourhood (Playwright-side spatial index, e.g. a simple R-tree as WebSee uses) instead of GWALI's implicit complete-graph comparison, to keep runtime near GWALI's own reported 3.65%-of-total comparison cost rather than its 60%-of-total MBR-collection cost.
2. **Adopt GWALI's two false-positive filters as an actionability gate, not just a diff filter:** (a) ignore alignment-relation changes on Text/* edges inside a container that has spare capacity; (b) require a direction-relation change to exceed an angle threshold (start at 45°, GWALI's validated value) before treating "A moved from north-of-B to east-of-B" as real. Apply both *before* deciding a cached anchor is stale and a fresh `elementFromPoint`/geometry re-query is needed.
3. **Use Kraus's strong/weak key split as the identity contract:** id/structural-path-like signals are strong (must match, or be Jaro-Winkler-similar above a validated t≈0.9); x/y/width/height/type are weak (checked for presence only) — in *every* matching mode, unlike ≈₂'s mistake of loosening a strong key without re-validating the threshold. This is directly implementable as a Playwright locator-scoring function reading `getBoundingClientRect()` + `aria snapshot` + DOM path, and is empirically what separates Kraus's 79–92% P/R from its own 21,440-false-positive ≈₂ failure mode (finding 6 above) — **do not** loosen a strong identity key's match test without the same care Kraus gave t and u.
4. **Reuse CLS's formula as the "is my cached geometry stale" trigger**, not just as a page-quality metric: compute `impact-fraction × distance-fraction` for a tracked element between "when I last resolved this locator" and "now," gated by the UA's ~3 px floor, and treat `hadRecentInput`/500 ms as a template for "was this shift caused by my own act step" (i.e. don't treat a shift immediately following your own `click()` as evidence of flake).
5. **Use Browserbite's centroid+size+orientation NCC-fallback as the last-resort recovery path when a DOM node disappears entirely**, not as the primary matcher: search a screenshot region around the element's last-known bounding box (its own ~40 px position / ~15 px size hand-tuned bounds are a reasonable seed, scaled per §5's recommendation 3) before falling back further to text/OCR.
6. **Borrow XFix's 3-term fitness (Δpos Euclidean, Δsize Σ|Δw|+|Δh|, Δneighbour-pos over N-hop DOM neighbours) as a post-action verification score**, not as a repair mechanism: after a `click`/`fill`, recompute Δpos/Δsize/Δneighbour-pos for the acted-on element (and its immediate DOM neighbours) between pre- and post-action snapshots to detect an unintended layout side-effect, exactly the signal XFix used to confirm a fix didn't break something else.
7. **Applitools's floating-region primitive (element rect ⊆ permitted-movement bounds rect) is the right tolerance *shape*** for "assert this element is still roughly here" — implement it directly over `getBoundingClientRect()` deltas rather than reinventing a scalar px threshold.
8. **Romano's taxonomy is the acceptance-test menu, not a mechanism to borrow:** a geometry-first locator's value proposition should be demonstrated specifically against the DOM Selector Issue (6.8%, 16/235) and Layout Difference (4.3%, 10/235) categories — and must be paired with an async-settle/quiescence wait, since Async Wait (45.1%) dwarfs both and a purely geometric stability check does nothing for it.

**Avoid:** pixel-only screenshot diffing as the *primary* detector — every screenshot-based source in this cluster (Browserbite bare-bones, WebSee, Chromatic Strict/Exact) needs either a learned classifier (Browserbite: F 0.79→0.923) or a perceptual/AA filter (Chromatic) layered on top to be usable, so a DOM-first tool should treat screenshots as a fallback signal, not the primary one. Avoid flat, unnormalised px cutoffs (Browserbite's 40/15 px is falsified by its own 70-px cited cross-browser example; Similo-family's 100-px linear location cutoff, read in the companion brief, was replaced under every tuned configuration) — normalise to viewport-fraction or element-relative-fraction per §5. Avoid loosening a strong identity key's equality test into a fuzzy-similarity test without a validated threshold the way Kraus's ≈₂ does to id/path — it is this cluster's clearest quantified cautionary number (21,440 vs 320 spurious diffs), and position/size were held constant (weak, presence-only) across all three of Kraus's relations, so the lesson is about validating *any* loosened identity key, not specifically position. Avoid raw-screenshot-pixel coordinates as a stored anchor for anything that must survive a zoom event — GUI-Perturbed's 3.3–7.9 pp drop is the direct citation against it; prefer post-layout CSS px / viewport-fraction, which zoom does not perturb the same way.

## 9. Open questions this cluster leaves

- **DPR and theme are entirely blank rows.** No source in this cluster runs a controlled device-pixel-ratio or light/dark-theme perturbation; both are pure gaps, not weak signals.
- **No source in this cluster isolates OS-level font-rendering/hinting drift from browser-engine drift.** Romano's one IE-artifact example and Kraus's "different DOMs or responsive design" hedge are the only mentions, and neither separates font metrics from layout-engine differences.
- **No cited tolerance-sweep compares raw-px vs. viewport-fraction vs. anchor-relative units head-to-head.** The recommendation in §5 to prefer normalised units is inferred from cross-source triangulation (CLS's own choice, Chromatic's own warning, GWALI's own 45°-threshold post-mortem), not from a single study that varied the unit and measured which generalises.
- **GUI-Perturbed's zoom result is about VLM screenshot grounding, not `getBoundingClientRect()`-based DOM geometry** — it is an open, untested question in this cluster whether a DOM-first locator that reads CSS px post-layout is genuinely immune to the zoom failure mode, or merely relocates the same risk (e.g. if it also caches a raw pixel screenshot for fallback matching).
- **GWALI's three false-positive-reducing heuristics (z-index flattening being the unaddressed one) were tuned on 54 apps** with no reported sensitivity analysis of the α=45° constant across a wider corpus, and no cross-check against Browserbite's or Kraus's corpora.
- **Vertical order and horizontal order are never measured as independent axes** in this cluster's sources — GWALI's North/South/East/West relation set and the ICSME severity study conflate them into one "movement" category (69%), so no cited number separates "elements reflowed to a new row" (vertical) from "elements reordered left-to-right" (horizontal).
- **Nearest-label relation has no isolated drift number anywhere in this cluster.** GWALI's k-NN neighbourhood is the closest representation of it, and Similo's 50-px-dilated neighbour-text window (read only as background in the companion brief) is the closest mechanism, but neither source reports how *often* or *how far* a label-to-target spatial relation itself drifts under any of the nine change axes.
- **Applitools's and Chromatic's own segmentation/matching algorithms are proprietary** — the only public numbers are default thresholds (0.063) and qualitative mode descriptions, so this cluster cannot report their actual false-positive/negative rates, leaving a genuine evidentiary gap for "what do commercial visual-testing dead-bands achieve in practice."
- **Nass et al., IST 2021 ("Why many challenges with GUI test automation (will) remain")** was in scope for this general research line but returned an Elsevier 403 and was not read; it may contain additional FP-cause taxonomy directly relevant to this cluster's question.
